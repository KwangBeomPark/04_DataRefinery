# 범용 DWH 개선계획: Opus 4회 논의 기록

작성일: 2026-11-03

대상: [주요 개발계획](FLEXIBLE_DWH_DEVELOPMENT_PLAN.md), [상세 개선계획](FLEXIBLE_DWH_IMPROVEMENT_PLAN.md).
설계 검토 기록이며 구현·DB 실행·성능 시험의 통과 기록이 아니다.

## 1. 실제 논의 방법과 확인 증빙

설치된 Claude CLI 2.1.287로 `claude-opus-5-5`, effort `high`를 명시해 총 네 차례 요청했다. 최초 2회 후 사용자 추가 지시에 따라 3·4차를 진행했다.
네 응답의 `modelUsage`와 `canonicalModel`이 모두 요청 모델과 일치했다. 종료 코드·성공 상태만이 아니라 응답 본문·완료 표식·해시·세션 ID를 함께 확인했다.

도구·MCP·파일 접근을 부여하지 않은 격리 실행이었다. 전달 범위는 계획, 확인한 코드의 동작 요약, 익명 설계 사례와 공개 기술 문서 요약이다.
실제 회사 CSV·DB·설정·회사 주소·인증정보를 검토 입력으로 제공하지 않았다. Opus가 저장소를 직접 검사하거나 테스트했다고 주장하지 않는다.

진행 순서는 **각 회차 비판 → 조정자의 수용/반박 → 수정 계획·이전 응답을 다음 요청에 포함 → 다음 회차 반례 점검 → 최종 계획 보완**이다.
3차는 사용자 흐름·업무 의미·운영 부담을, 4차는 A~H의 구체적인 실패/자원/배포 사례와 여러 관점의 완료 기준을 중점 검토했다.
같은 질문을 반복하고 합의로 간주한 방식이 아니다.

로컬 원본은 Git에서 제외된 `tools/dwh-plan-review-20261103/`에 보관한다.
각 회차의 `round-N-prompt.txt`, `round-N-response.json`, `round-N-review.md`, `round-N-receipt.json`, stderr 파일과 중간 조정 의견이 포함된다.

| 논점 | 최종 판단과 이유 |
| --- | --- |
| 기존 재생성 엔진과 증분 엔진 | 소유 작업 공간을 분리. 기존 기능의 강제 동결은 철회하고 기존 DB는 검증된 전환 전까지 새 엔진이 변경하지 않음 |
| 키·팩트 갱신 | 등록부·차원·팩트를 같은 DB와 트랜잭션에서 확정. 업무 키 정규화도 버전화 |

| SharePoint | 직접 업로드 요구를 유지. 동기화 폴더 저장을 클라우드 배포 완료로 격하하지 않음 |
| 보관·분할 | 자동 실행하지 않음. 키 권위·기간 위치·교차 연도 조회·과거 수정과 다중 DB 원자성 제약을 먼저 설계 |

## 3. 2차 논의에서 추가한 장치

- **예산 소유자**: 물리 작업 공간 단위로 확정. 첫 구현은 모델 1개 = 작업 공간 1개이며 이후 분할해도 활성 DB·WAL 합계를 유지한다.
- **복구 자료**: 교체 범위의 이전 행뿐 아니라 변경되는 차원 속성·메타데이터도 보존하고 체크섬·행 수를 확인한다. 매월 전체 DB 복사를 의무화하지 않는다.
- **대리키 발급**: 쓰기 잠금 아래 등록부와 같은 트랜잭션에서 할당한다. SEQUENCE 롤백이나 빈 번호 없는 연속성을 가정하지 않는다.
- **완성 범위 확인**: 선언 범위·실제 데이터·통제합계를 대조한다. 의도적인 0건/삭제는 명시하며 누락을 삭제로 해석하지 않는다.
- **정의 버전**: 안정적인 모델/팩트 ID와 정의 버전을 분리한다. 같은 범위의 정의 변경은 재도출이며 새 범위의 중복 누적이 아니다.
- **측정 출처**: 시각·수집 방법·추정 신뢰도를 표시한다. WAL 없음=0, 접근 실패=알 수 없음. 부분 측정으로 정상 사용률을 표시하지 않는다.
- **단계 축소**: 폼 기반 모델 지정·자동 관계도를 먼저 제공한다. 읽기 전용 DB 검사기는 실행기와 병행 개발해 실제 구조 검수에 쓴다.
- **외부 전제**: 승인된 DuckDB 실행 환경과 SharePoint 인증·권한 가능성을 초기에 확인한다.

## 4. 2차 제안을 그대로 채택하지 않은 부분

| 제안/가정 | 조정 내용 |
| --- | --- |
| 로컬 DuckDB 로딩 차단이면 전체 작업 중단 | 네이티브 통합 검증은 보류. 계획·UI 설계·모의 검사는 계속 가능. 보안 정책은 우회하지 않음 |
| 예비 실행 1회 결과에 1.5배를 곱해 실행 허용 | 보장치로 채택하지 않음. 작은 완성 범위부터 측정하고 순차 재평가. 근거 없는 거대 쓰기는 분석 단계에서 멈춤 |
| 임시 디렉터리 한도로 디스크 보호 | spill 한도만 제한. DB·WAL·출력·다른 프로세스의 사용량까지 보호한다고 설명하지 않음 |
| 데이터 트랜잭션 뒤 성공 이력 갱신 | 성공 이력·범위 상태·리비전도 데이터와 같은 트랜잭션에서 확정. 재시작 때 중단 실행을 조정 |
| quickXorHash가 있으면 추가 검증 불필요 | 동일 알고리즘 비교는 전송 오류 검증 수준으로 기록. SHA-256 증명과 구분. 비교 불가면 읽기 검증 또는 미검증 표시 |
| 같은 경로 업로드 교체면 모든 게시 안전성 확보 | 원격 커밋과 사후 내용 검증의 시간 차이를 명시. ETag 충돌과 검증 실패·조건부 복구를 시험. 엄격한 노출 제어는 별도 버전/포인터 계약 필요 |
| 예비 실행 파일은 종료 후 삭제 | 앱 소유 경로·잠금·상태와 보존 정책 확인 후 별도 정리. 사용자 DB/WAL 자동 삭제 금지 |

## 5. 3차 논의: 실제 업무·사용자 흐름의 보완

| 지적 | 반영한 최소 수정 |
| --- | --- |
| 과거 월 정정이 최신 속성을 회귀시킴 | 속성 권위 원천·기준시점·고정 정책 명시. 예전 기간이 최신 값을 덮어쓰지 않으며 동률 상충 차단 |
| CSV에 집계 의미가 전달되지 않음 | 첫 기본 출력은 가산 wide CSV. 비용 long에는 반복 QTY 제외. 재고 단일기간·비율 구성요소부터 시작하고 다기간/측정값은 실제 Excel 템플릿 시험 후 확장 |
| CSV 축소가 DB 경고의 해결책으로 보임 | 활성 DB, 이력 포함 작업 공간, CSV/Excel의 세 패널과 대응을 분리 |
| 새 비용 열·이름 변경이 누락될 수 있음 | 구조 대조·역할 분류·정의 버전/재도출 목록. 과거 새 지표는 미보고 NULL |
| 차원 재사용과 다른 공간의 SK 충돌 | 공간 간에는 설계 템플릿 복사. 내부 키는 기본 출력 제외, 교차 공간 조인은 첫 범위 제외 |
| 첫 엔진에 사용자 입력 폼이 없음 | 최소 설정 마법사를 엔진과 함께 구현. 관계도 자유 편집은 후속 |
| 운영·계측이 너무 복잡함 | 앱 전체 디스크 집약 작업 순차 실행, DB 조회 직렬화, 쓰기 중 캐시 표본, 전체 대사는 명시적 작업 |

그대로 수용하지 않은 제안:

- `as_of` 동률에서 나중 적재 우선은 입력 순서 독립적이지 않다. 상충은 명시적으로 해결한다.
- 매 커밋 전체 등록부를 담는 외부 목록은 작다고 보장할 수 없고 DB와 원자적이지 않다. 동일 키 재생을 무조건 약속하지 않는다.
- 속성의 `load_id`만 보고 과거 값을 되돌리는 방식은 후속 변경까지 안전하게 복원한다고 보기 어렵다. 첫 버전에 확정 후 undo는 제공하지 않는다.
- 표본 200행마다 업무 키 전체 정렬을 강제하거나 같은 커서를 여러 스레드가 안전하게 공유한다고 가정하지 않는다.
- 행 수 보존식만으로 비대상 금액 불변·대사 일치를 증명하지 않는다. 범위 술어·통제합계와 실제 회귀 시험을 사용한다.
- 반복 QTY의 동반 팩트를 자동 생성하는 기능은 첫 최소 범위에 포함하지 않는다. 원본 행 기준이 모호하면 임의 MAX/중복 제거로 보정하지 않는다.

## 6. 4차 논의: 반례와 최종 조정

4차는 DB 경고와 디스크 부족, 알 수 없는 WAL, 후속 분할 합계, 불완전/변경 입력, 과거 속성·DB 손상, 잘못된 피벗, 원격 검증/충돌을 A~H 반례로 점검했다.
기대 동작과 여섯 관점의 증빙은 상세계획 10.1~10.2에 정리했다. 이는 실제 시험 결과가 아니다.

채택한 내용:

- 단일 팩트·가산 CSV·고정 파일 게시를 첫 수직 시제품의 중심으로 좁힌다.
- 막연한 '최신값 덮어쓰기'와 과거 속성 복원 문구를 구체적인 권위/기준시점·감사 사본 계약으로 교체한다.
- 확정 전 롤백, 확정 후 정정, DB 전체 손상 복원 지점을 서로 구분한다. 복원 지점 이후 정보가 불완전할 수 있음을 표시한다.
- 필수 자원 점검 실패는 확인 후 쓰기 보류, 부가 통계 미지원은 알 수 없음으로 구분한다.
- 이전 원격본 보존 여부와 소비자 Excel 새로고침 여부를 게시 성공과 별개 상태로 표시한다.
- 후속 분할의 공통 등록부는 한 작업 공간 내부의 권위다. 여러 작업 공간의 키 통합을 의미하지 않는다.

4차 이후 조정자가 다시 수정한 내용:

| 4차 제안/표현 | 최종 판단 |
| --- | --- |
| 첫 실행은 입력 바이트×k 여유만 있으면 허용 | 실행 허용의 단독 규칙으로 거부. 합성·격리 시험으로 검증한 지원 경계와 공간 추정 프로필 안의 작은 완성 범위부터 실행. 근거가 없으면 읽기 분석까지만 수행 |
| A의 예산/가용 수치로 쓰기 허용을 단정 | 81%는 권고 경고만 결정. 작업 피크·다른 볼륨·필수 점검을 통과해야 실제 쓰기 판단 가능 |
| WAL 접근 거부는 DB 비정상임을 뜻함 | 측정/권한/경합 원인을 확인하며 손상으로 단정하지 않음. 필수 점검 불가 시 쓰기는 보류 |
| 모든 속성에 기준시점 필수 | 불변 속성은 고정 정책으로 충분. 변경 가능한 속성은 비교 가능한 기준시점·권위 원천 명시 |
| 백업 이후 범위는 외부 일지로 모두 식별 | 일지 자체가 누락될 수 있으므로 완전성 보장하지 않음. 원본/활성 범위 대조 전에는 이후 상태 확인 필요 |
| 복원 후 달라진 SK는 CSV에 없으니 의미 동일 | 동일 DB의 투명 복구로 부르지 않음. 새 복구 세대에서 전체 대사·출력 재승인·외부 의존성 재검증 |
| 버전 관리 켜짐+ID 기록이면 이전 원격본 있음 | 실제 조회/복구 가능 여부까지 확인한 경우만 보존 확인으로 표시 |
| '미등록 키 차단'이 신규 멤버까지 차단할 가능성 | 최종 대조에서 신규 업무 키의 정상 등록과 필수 키 누락/마스터 참조 오류를 분리. 새 달의 정상 신규 거래선·제품은 같은 트랜잭션에서 등록 |

Opus는 4차 응답에서 동률 최신 적재의 결정성, 속성 load_id 되돌림, 매번 외부 등록부 복사, 원본만으로 키 복원, 정렬 표본 강제, 행 수만의 대사, 커서 동시 사용, 동반 팩트 자동 생성, 모든 실패의 이전본 보존 문구를 철회/수정했다.
최종 계획에 남은 불확실성을 합의만으로 해소된 것처럼 보고하지 않는다.

## 7. 최종 계획의 적용 위치와 남은 결정

- 상세계획 3~4장: 유연한 모델·키·월별 누적·수정·복구.
- 상세계획 5~6장: 80% 경고·건강 지표·디스크 보호·보관/분할.
- 상세계획 7~8장: 승인된 목적별 CSV·SharePoint·Excel 계약.
- 상세계획 9~10장: 단계별 완료 기준·합성/현장 검증.
- 상세계획 12장: 예산 크기, 보존 기간, 완성 선언 주체, 차원 이력, 회사 인증/권한, Excel 성능 목표.

계획 작성 중 로컬 Python의 `_duckdb` 로딩이 Application Control에 차단됨을 확인했다. DB 연결 전 발생했으며 정책 변경·우회는 하지 않았다.
해당 환경에서 계측 API·강제 종료·디스크 부족·실제 데이터 성능 검증은 실행되지 않았다. 이 제한은 실행 환경 확인 단계의 항목으로 남긴다.
이번 결과는 계획 문서이며 앱·사용자 DB·공개 CSV·서명 배포물·GitHub 릴리즈를 변경하지 않았다.
