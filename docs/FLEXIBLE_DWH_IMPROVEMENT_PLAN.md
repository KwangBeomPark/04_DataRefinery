# Data Refinery 범용 DWH·배포 개선계획

작성일: 2026-11-03

상태: Claude Opus 5.5와 총 4회 논의 후 보완한 개선계획. 구현 완료 문서가 아니다.
기준: v2.7.0 소스와 `FLEXIBLE_DWH_DEVELOPMENT_PLAN.md`의 사용자 요구사항.
소스 기준 커밋: `7e152ce7e6beddb20a571cdd9c6d6186e437c062`.
검토의 수용·수정 사유와 실제 응답 증빙은 [Opus 논의 기록](FLEXIBLE_DWH_OPUS_REVIEW.md)에 정리한다.

## 1. 제품 범위와 사용자 흐름

원본마다 데이터 모델을 정의하고 기존 DuckDB에 누적한 뒤, 앱 안에서 구조·데이터·원본 대사를 확인한다.
검수한 DB에서 여러 목적별 CSV를 만들고 회사 SharePoint로 배포해 Excel에서 가져와 피벗 분석한다.
수익성은 최초 검증 사례이며 매출·매출차감·재고에 같은 구조를 강제하지 않는다.

```mermaid
flowchart LR
    A[원본 연결] --> B[차원·팩트·관계 정의]
    B --> C[용량 사전 점검]
    C --> D[누적·수정 범위 반영]
    D --> E[구조·대사·용량 확인]
    E --> F[목적별 CSV 생성·승인]
    F --> G[SharePoint 업로드·검증]
    G --> H[Excel 새로고침·피벗]
```

- 팀원 PC에 DuckDB·Python·ODBC를 추가 설치하지 않는다.
- 첫 구현은 모델 1개 = 작업 공간 1개 = 활성 DuckDB 1개로 시작한다. 여러 작업 공간을 작업 목록에서 관리한다. 첫 수직 시제품의 팩트는 하나로 제한한다.
- 모델 정의, 출력 정의, 배포 프로필을 분리하고 참조로 연결한다. 중간 파일을 탭 사이에 반복해서 옮기게 하지 않는다.
- 기존 파일 집계·CSV 누적·배포·레거시 실행 경로를 보존한다. 전환 대상으로 선택하지 않은 기존 DB를 바꾸지 않는다.
- 회사 자료·설정·인증서·기존 서명 배포본을 계획 검수나 시험 목적으로 변경하지 않는다.

## 2. 현행 코드와 재사용 경계

| 확인한 경로 | 현재 동작 | 개선 시 취급 |
| --- | --- | --- |
| `src/qt/tabs/dwh_tab.py`와 루트 DWH 모듈 | 별도 마스터 입력, 고정 손익·달력, 팩트 재생성, Parquet 결과 미리보기 | 새 누적 작업은 별도 모델·작업 공간에서 시작. 동일 DB를 두 엔진이 함께 변경하지 않음 |
| `src/dimension_builder.py` | 정렬한 업무 키에 번호를 다시 부여 | 증분 DWH의 키 발급기로 그대로 사용하지 않음 |
| `src/dwh/dimension_builder.py` | 영속 대리키 등록부 | 등록부·키 안정성 로직을 새 모델 실행기에 맞춰 재사용 검토 |
| `src/dataset_engine.py` | 파일 지문, 기간별 교체, 불완전 기여분 차단, 검사·승인·CSV 공개 | 안전 장치를 어댑터와 공통 계약으로 재사용. 단일 `dataset_records`를 범용 차원·팩트로 간주하지 않음 |
| 현재 미리보기 | 최종 Parquet의 상위 50/100/200행과 일부 열 | 실제 DB 카탈로그·테이블·관계·전체 검사 화면으로 확장 |

기존 엔진을 즉시 폐기하거나 읽기 전용으로 강제 전환하지 않는다. 데이터·설정 호환 시험을 먼저 수행한다.
새 엔진은 엔진 ID·스키마 버전·작업 공간 ID를 확인한 자기 소유 DB만 변경한다. 표식이 없는 기존 DB는 진단/전환 대상으로만 연다.
작업 DB·설정의 기준 위치는 `src/app_paths.py`의 설치 폴더 내 `UserSetting/datasets`이며 기존 이관·보존 규칙을 따른다.
실제 설정 경로의 UNC·동기화·재분석 지점·클라우드 파일 특성을 확인한다. 이 기준 경로가 자동으로 OneDrive 리디렉션된다고 가정하지 않는다.

## 3. 모델·키·지표 계약

- 모델에는 원본, 열 연결, 업무 키 정규화, 차원 속성, 팩트 행 기준, 지표·단위·집계 방식, 입력 범위·갱신 정책을 저장한다.
- 기본 UI는 원본 열 목록 / 모델 카드·관계 / 선택 항목 설정 / 데이터·검사 결과의 네 영역으로 구성한다. 입력 폼과 자동 배치된 읽기 전용 관계도를 먼저 구현하며 자유 드래그 편집은 후속 확장이다. 사용자가 JSON을 작성하게 하지 않는다.
- 차원 대리키와 등록부는 첫 구현에서 같은 DuckDB 안에 두고 팩트 변경과 같은 트랜잭션에서 확정한다.
- 작업 공간 쓰기 잠금 아래 기존 검증된 등록부 할당을 재사용한다. 새 키는 등록부 최댓값과 신규 고유 키 순번으로 배정하며 SEQUENCE의 롤백/연속성을 가정하지 않는다. 미확정 번호를 영속 ID로 외부에 노출하지 않는다.
- 업무 키의 공백·대소문자·문자형·선행 0 규칙을 버전화한다. 기존 등록부의 UPPER/TRIM을 모든 모델에 강제하지 않는다. 복합키는 열별로 정규화한 구조화 값으로 관리하고 구분자 단순 결합으로 충돌시키지 않는다. 변경 시 조용히 재번호를 부여하지 않고 영향 분석과 전환 절차를 거친다.
- 팩트의 중복은 업무상 행 기준으로 검사한다. 행 식별 ID만으로 중복 적재를 막았다고 판단하지 않는다.
- 차원 이름이 같다는 이유만으로 공유하지 않는다. 키의 범위·의미·정규화·이력 정책이 같을 때만 연결한다.
- 작업 공간 사이의 재사용은 버전 있는 차원 정의 템플릿 복사다. 차원 데이터·등록부·대리키는 작업 공간 소유이며, 다른 공간의 정수 키가 같다고 조인하지 않는다. 기본 CSV에는 내부 대리키를 노출하지 않는다.
- 같은 작업 공간의 여러 팩트는 동일 차원을 참조할 수 있다. 첫 수직 구현은 한 팩트로 검증하며 교차 작업 공간 통합과 다중 팩트 통합 출력은 후속 검증 범위다.
- 월·일 등 시간 수준과 기간 범위는 원본·모델에서 결정한다. 2025~2027년 고정 달력을 새 모델에 사용하지 않는다.
- 새 업무 키는 지정한 차원 원천에서 고유성·필수 속성을 검증해 정상 신규 멤버로 등록한다. 중단 대상은 필수 업무 키 누락·상충이나 지정 마스터/차원 원천에 없는 참조 키다. 신규 멤버를 모두 오류로 취급하지 않는다. 미분류 멤버 허용은 모델별 명시적 정책과 별도 건수·금액 표시가 있을 때만 가능하다.
- 최초 속성 정책은 '고정: 상충 시 확인' 또는 '선언 기준시점의 최신값'이다. 후자는 같은 권위 원천의 비교 가능한 기준시점을 사용하고, 이전 시점은 보고 후 유지·같은 시점의 상충은 차단한다. 적재 순서를 최신값의 기준으로 쓰지 않는다. 과거 출력에도 현재 속성이 표시되는 Type1의 영향을 알리고 승인 스냅샷을 보존한다. SCD2는 후속 확장이다.
- 매출은 합계, 재고는 기준일/월말 잔액·평균 등 원천에 맞는 규칙을 적용한다. 비율은 분자·분모에서 계산한다.
- 이번 수익성 사례의 USD·QTY 배율 1, 원본 소수점 보존은 해당 모델의 설정이며 전역 기본값이 아니다.
- 금액은 원본 문자열에서 선언한 정밀도의 DECIMAL로 변환한다. 단위 배수와 소수 자릿수를 구분하고 조용한 반올림·범위 초과를 허용하지 않는다. 비율의 계산·표시 정밀도와 0/NULL 분모 정책은 따로 정한다.
- 테이블·열 이름은 식별자로 검증·인용하고 값은 매개변수로 전달한다. 화면 문자열을 그대로 SQL로 연결하지 않는다.

### 3.1 과거 수정·원본 구조 변경의 경계

- 변경 가능한 차원 속성마다 기준시점과 권위 원천 하나를 모델에 명시한다. 월 기준인지, 별도 추출일/마스터 기준인지 구분하고 파일 mtime을 사용하지 않는다. 같은 시점의 상충 해결은 결정·사유와 함께 모델/규칙 버전으로 남긴다. 불변 속성은 '고정' 정책을 사용한다.
- 수정 2월이 4월의 최신 속성을 자동으로 되돌리지 않게 한다. 같은 기준시점의 상충 값은 적재 순서로 임의 선택하지 않고 변경 목록에서 확인한다. 단순히 '나중 적재 우선'을 결정적 규칙이라고 하지 않는다.
- 첫 구현은 확정 후의 무제한 실행 취소를 제공하지 않는다. 과거 범위는 검수한 완성 입력으로 재처리한다. 이후 차원 갱신이 있는 상태에서 이전 속성 사본을 일괄 복원하지 않는다.
- 적재 전에 동일/새 열/누락 열/형식 변경을 대조한다. 새 열의 지표·속성·명시적 제외 역할이 정해질 때까지 확정하지 않는다. 기존 필수 열 누락·변환 실패는 차단한다.
- 이름 변경은 기존 필드에 명시적으로 다시 연결한다. 새 선택 지표의 과거 값은 미보고 NULL이며 0과 구분한다. 파생 합계에서 NULL을 다루는 규칙도 저장한다.
- 호환 추가, 범위 재도출 필요, 키/행 기준의 파괴적 변경을 구분한다. 파괴적 변경은 첫 구현에서 새 작업 공간으로 검증하며 기존 공간을 자동 전환하지 않는다.
- 최소 지표 정의는 단위·단위 배수·소수 자릿수·부호·NULL 의미·행 기준·시간 집계 규칙이다. 같은 단위가 아닌 값을 하나의 합계로 섞지 않는다.

## 4. 누적·수정 범위·복구

첫 구현의 확정 적재 단위는 **완성된 논리 범위의 스냅샷**이다. 전체 DB 재작성은 기본 월간 작업이 아니다.

- 새 월은 추가하고 수정 월은 해당 모델·팩트·기간과 모델이 선택한 분할 범위만 교체한다. 법인은 분할 열의 예시이며 필수 고정 열이 아니다.
- 범위별 구성 파일과 완성 선언을 관리한다. 여러 파일 중 일부만 들어오면 스테이징·진단까지만 허용하고 확정 교체하지 않는다.
- 선언 범위와 입력에서 계산한 실제 범위·통제합계를 대조한다. 파일만으로 완성을 증명할 수 없으면 원천 통제 또는 담당자의 완성 선언을 기록한다. 의도적인 0건/삭제 범위는 별도로 선언해야 하며 누락을 삭제로 해석하지 않는다.
- 범위 식별은 안정적인 모델 ID·팩트 ID를 사용한다. 정의 버전 변경은 같은 범위의 재도출/전환이며 자동으로 별도 범위를 만들어 이중 누적하지 않는다.
- 파일 내용 해시·입력 집합·모델/변환 정의 버전을 이용해 같은 반영을 중복 수행하지 않는다. 이름이나 mtime만으로 동일성을 판단하지 않는다.
- 입력 지문은 읽기 전후·확정 전에 대조한다. 앱 소유 작업 사본의 내용 해시로 실제 읽은 입력을 고정하고 그 공간/IO를 계측한다. 원본이 복사/읽기 중 바뀌면 확정하지 않는다. 확정 후 원본 변경은 다음 입력으로 다루며 이미 확정한 자료를 자동 되돌리지 않는다. 모델의 속성·분류만 바뀐 경우와 동일 자료 재실행도 구분한다.
- 교체 전 쓰기 잠금을 잡고 교체 범위의 이전 행과 차원 속성 변경 내역을 감사·차이 비교 자료로 보존한다. 행 수·체크섬을 검증한 뒤 교체한다. 이 자료를 임의 시점 복원 기능으로 안내하지 않는다.
- 한 범위의 등록부·차원·팩트·범위 상태·대사 결과·DB 리비전·적재 성공 상태를 같은 트랜잭션 T에서 확정한다. 데이터 커밋 후 별도로 성공 이력을 기록하는 틈을 만들지 않는다.
- 실행 시작 이력은 별도로 남길 수 있으나 커밋되지 않은 실행과 중단 상태는 재시작 시 DB의 확정 이력에 맞춰 조정한다. 실패 로그는 롤백 후 별도 기록한다.
- 교체 대상의 전후 합계와 비대상 범위의 통제값을 기록한다. 감사 사본은 공간 사전 점검·보존 정책 대상이며 커밋 실패 후 임의로 삭제하지 않는다. 첫 버전에는 확정 후 되돌리기 버튼을 두지 않는다.
- 실패 시 기존 성공 자료를 보존한다. 강제 종료·디스크 부족 복구는 지정 DuckDB 버전에서 실제 시험한다.
- 작업 식별자와 논리 DB 리비전으로 원본→적재→출력의 계보를 남긴다.
- 첫 구현은 일부 거래만 담긴 취소·갱신 델타를 완성 월로 취급하지 않는다. 전표 기반 upsert·취소 정책을 지원하기 전에는 명확히 안내한다.
- 매월 전체 DB 사본을 의무 생성하지 않는다. 변경 범위의 이력·원본·승인 결과를 보존하고, 별도 전체 백업은 닫힌/일관된 상태와 용량을 검증한 관리 작업으로 둔다.
- 범위 사전 이미지는 DB 전체 손상에 대비한 백업을 대체하지 않는다. 일관 백업·복원 시험과 마지막 복구 가능 리비전/보관 원본을 관리한다. DB 밖 파일 기록과 DB 커밋의 원자성을 가정하지 않는다.
- 원본만 재적재하면 대리키·정의·마스터·속성 이력까지 동일하게 복원된다고 보장하지 않는다. 전체 등록부를 '작은 목록'으로 매 커밋 복사하는 안은 기본으로 채택하지 않는다.

DB 반영 성공과 CSV·SharePoint 게시 성공은 다른 상태다. 게시 실패를 DB 적재 실패로 숨기거나, 새 DB가 반영됐다고 이전 공개 파일을 지우지 않는다.

### 4.1 일관 백업·복원 지점

- 수동 관리 작업으로 쓰기 대기열 중지 → CHECKPOINT 성공 확인 → 연결 정리/정상 종료 → 새 사본 생성 → 사본 읽기 전용 검사 → 복원 지점 등록을 검증한다. 필요한 복사 공간을 먼저 점검하고 사용자 WAL을 삭제하지 않는다.
- 백업은 DB의 등록부·모델·범위 상태·리비전을 포함해야 한다. 외부 원본/규칙 파일도 필요한 버전·해시와 실제 보존 여부를 연결한다. 마지막 복원 가능 리비전과 이후 자료의 보장 범위를 표시한다.
- 손상 복원은 새 작업 공간/복구 세대에서 검수한다. 기존 파일을 보존하고 이전 승인·게시 작업을 자동 재사용하지 않는다. 확정 전 실패의 트랜잭션 롤백과 이 작업을 구분한다.
- 복원 지점 이후의 외부 일지는 누락될 수 있는 보조 정보다. 일지에 없다고 추가 자료가 없다고 판단하지 않는다. 누적 대상 기간/원본을 대조하기 전에는 '그 이후 상태 확인 필요'로 남긴다.
- 백업 이후 재적재에서 새 대리키가 달라질 수 있으면 동일 DB의 무손실 복구라고 부르지 않는다. 새 세대의 전체 대사·출력 재승인이 필요하다. 테스트된 등록부/정의/원본 계보가 없으면 동일 키 재생을 보장하지 않는다.
- 읽기·복원 시험을 통과하기 전에는 재해 복구 지원 완료로 표시하지 않는다. 정기 백업 자동화·장기 보존 주기는 후속 운영값이며 무조건 매월 전체 DB 사본을 만들지는 않는다.

## 5. 용량·성능 관리 지표

### 5.1 80% 경고의 정확한 의미

DuckDB의 최대 파일 크기나 성능 한계를 80%로 정의하지 않는다. 앱의 **작업 공간별 활성 DB 운영 예산 B**를 별도로 둔다.
작업 공간은 한 모델의 DB·이력·출력 정의를 관리하는 단위다. 첫 구현은 모델과 작업 공간이 1:1이므로 사용자에게 해당 모델 이름으로 보여준다.

- 분자 U: 해당 작업 공간의 활성 DuckDB 파일 길이와 해당 WAL 파일 길이 합계. 각 항목도 따로 표시한다.
- 분모 B: 사용자가 설정한 양수 바이트 예산. 표시 단위는 GiB로 통일한다.
- 경고: `U / B >= 0.80`. 경고 해제는 75% 미만을 기본 제안으로 하여 알림 반복을 줄인다.
- 예: 10 GiB 예산에서 8 GiB부터 경고한다. 설명용 예시이며 기본 성능 한도나 권장 DB 크기가 아니다.
- B가 없으면 `운영 한도 미설정`과 실제 크기를 표시한다. 임의 비율·정상 판정을 만들지 않는다.
- 첫 설정은 '적재 후 설정'을 허용한다. 비교 가능한 신규 기간 실측이 충분히 쌓이면 보유 기간·증가 범위·디스크/작업 피크를 보여주고 임시 운영 예산을 제안한다. 제안값은 자동 확정하거나 성능 한계라고 표시하지 않는다.
- 예산 도달 예상은 비교 가능한 양의 증가 근거가 있을 때 범위·신뢰도와 함께 표시한다. 재사용 블록 때문에 관측 증가가 0인 경우 무한히 저장 가능하다고 추정하지 않는다. 수정 작업의 팽창은 별도 추적으로 남긴다.
- 100%는 운영 정책 초과 표시이며 DB의 물리적 만료나 자동 삭제 조건이 아니다. 반복 확인창 대신 지속 배너와 실행 이력으로 알린다.
- 나중에 파일을 분할해도 같은 작업 공간의 활성 DB·WAL 합산을 유지한다. 분할만으로 경고와 전체 점유를 감추지 않는다. 보관본은 별도 보관 용량과 전체 점유에 남긴다.
- DuckDB의 `memory_limit`이나 RAM 비율은 이 DB 예산과 전혀 다른 지표다.

### 5.2 화면에 보여줄 값과 측정 의미

| 지표 | 의미·수집 시점 | 해석 제한 |
| --- | --- | --- |
| 활성 DB·WAL 크기와 U/B | 파일별 길이, 작업 공간 합계, 측정 시각 | 순차 측정 중 변경 가능. 미설정 예산은 % 없음 |
| 작업 공간 사용량 | DB·원본 보관·스테이징·임시·이력·CSV의 중복 경로 없는 합계 | 파일 길이 합계이며 OS의 실제 할당 블록·볼륨 사용량과 구분 |
| 볼륨별 사용 가능한 공간 | 작업 경로가 놓인 볼륨에서 호출자에게 허용된 여유, 쿼터 지원 여부 | Cloud PC/가상 드라이브가 제공하지 않으면 알 수 없음으로 표시 |
| 내부 사용/재사용 블록 | `database_size`의 블록 정보, 안전한 작업 경계에서 조회 | free_blocks는 DB 내부 재사용 공간. 디스크 여유 공간에 더하지 않음 |
| 메모리 | 프로세스 RSS, DuckDB 버퍼 사용/설정 한도, 시스템 여유 | 버퍼 한도는 전체 프로세스 메모리의 완전한 상한이 아님 |
| 임시 작업 공간 | 실제 임시 파일 점유와 런타임 설정 한도 | 설정 기본값은 버전·환경에서 읽고 추정하지 않음 |
| 데이터 증가 | 기간·테이블별 행 수, 성공 작업의 크기 변화·증가 추세 | 테이블별 정확한 바이트를 알 수 없으면 추정임을 표시하거나 생략 |
| 처리 성능 | 스캔·적재·대사·CSV·업로드 시간과 처리량 | 같은 모델·작업·규모의 이력끼리 비교. DB 크기만으로 저하 단정 금지 |

파일·OS 상태는 제한된 간격으로 수집하고, DB 메타 쿼리는 같은 프로세스의 안전한 실행 지점에서 수집한다.
타이머에서 전체 테이블 COUNT나 업무 쿼리를 반복하지 않는다. 미지원·실패·오래된 측정에는 사유와 시각을 표시한다.
측정 레코드는 값·바이트 단위·수집 API·대상·시각·상태·추정 신뢰도를 갖는다. WAL 파일이 실제로 없으면 0이며 접근 실패는 알 수 없음이다.
구성 요소가 누락되면 알려진 합계의 하한과 누락 항목을 표시하고 전체 사용률·정상 판정을 만들지 않는다. 이전 측정은 오래된 값으로 표시한다.

### 5.3 적재 전·중 공간 보호

- 적재·수정·CSV 생성·보관 작업마다 DB/WAL, staging/spill, 새 파일과 이전 공개본의 동시 보유, 필요한 복구 사본을 확인한다.
- DB·임시·CSV·보관 위치가 다르면 볼륨별로 비용을 배분한다. 같은 볼륨의 여유 공간을 여러 경로마다 중복 가산하지 않는다.
- 예상 피크 작업 공간과 최소 잔여 여유가 가용 공간보다 크면 쓰기를 시작하지 않는다.
- 최소 잔여 여유 초기값은 2 GiB를 시험용 제안으로 두되 Cloud PC/쿼터·합성 저용량 시험 후 확정한다. 전체 볼륨의 고정 5% 규칙은 적용하지 않는다. 예약 여유는 예상 작업 공간을 대체하지 않는다.
- 입력 바이트나 DB 크기의 고정 배수만으로 필요한 공간을 보장하지 않는다. 연산 계획·표본 특성·성공 작업의 피크를 이용하고 추정 신뢰도를 표시한다.
- 최초 실행은 작은 완성 범위를 새 작업 공간에서 순차 처리하고 첫 성공 적재 자체를 실측으로 사용한다. 별도 복제 프로브 DB를 의무로 만들지 않으며 기존 사용자 DB로 실험하지 않는다. 앞부분 몇 행이나 실측 1회에 고정 1.5배를 곱한 값을 보장치로 취급하지 않는다.
- 초기 누적은 범위를 순차 처리하며 범위 사이에 공간·추정을 갱신한다. 통제할 수 없는 큰 범위와 불명확한 소요 공간은 분석까지만 허용하고 분할 입력·추가 공간 등 실행 가능한 조건을 먼저 확보한다.
- 첫 운영 실행의 근거는 승인 환경의 합성 자료에서 검증한 작업 종류·자료형·연산/규모 경계와 공간 추정 프로필이다. 그 경계 내의 작은 완성 범위만 첫 실측 대상으로 허용한다. 프로필/추정이 없거나 벗어나면 읽기 분석까지만 수행하고 먼저 격리 시험으로 경계를 확립한다.
- 입력 바이트×k만으로 첫 실행 허용을 결정하는 규칙은 채택하지 않는다. 검증된 경계·실측 추정도 모든 외부 디스크 사용을 통제하는 보장은 아니며 잔여 위험과 실행 중 감시를 함께 표시한다.
- 임시 디렉터리·버퍼 한도를 명시한다. 임시 한도는 DB·WAL·출력·다른 프로세스의 사용량까지 제한하는 장치가 아니며 전체 디스크 보호를 보장하지 않는다.
- 실행 중 가용 공간을 다시 확인한다. 임계 부족 시 새 쓰기 중지·취소·복구를 시도하되, 인터럽트/커밋/WAL 복구의 실제 동작은 버전별 시험으로 확정한다.
- 첫 구현은 앱 전체의 디스크 집약 작업을 한 대기열에서 순차 실행하고 작업 공간 쓰기 잠금을 둔다. 여러 앱 인스턴스의 동일 DB 접근도 차단한다. 여러 동시 작업의 볼륨별 예약 조정은 후속으로 미룬다. 다른 앱의 디스크 사용은 계속 변할 수 있다.
- 예비 실행 자료 정리는 앱 소유 경로·작업 상태·잠금과 보존 정책을 확인한 별도 동작으로 둔다. 사용자 DB·WAL을 자동 정리 대상으로 삼지 않는다.
- 커밋·체크포인트·강제 종료/공간 부족 복구 시험이 안전하지 않으면 해당 쓰기 경로를 제공하지 않는다. 백업 필요성과 자원 설계를 재평가한다.
- 필수 디스크 사전 점검이나 활성 DB/WAL 상태 확인에 실패하면 재확인 후 쓰기를 보류한다. 이를 곧바로 DB 손상으로 단정하지 않는다. RSS 등 부가 통계 미지원은 알 수 없음으로 표시하며 동일한 차단 사유로 취급하지 않는다.

### 5.4 경고 화면과 대응

용량 패널에는 현재 사용/한도, 남은 디스크, 증가 추세, 최근 작업시간, 예측 근거를 보여준다.
80% 알림에는 해당 예산과 측정값, 다음 작업의 예상 부담, 선택할 수 있는 대응을 함께 표시한다.

- 활성 DB 패널: 예산/디스크 재검토, 내부 재사용 공간 확인, 후속 보관·분할 검토. CSV를 줄여도 DB 사용률은 줄지 않는다고 표시한다.
- 전체 작업 공간 패널: 원본·사전 이미지·이력 보존 정책과 실제 점유를 검토한다. 자동 삭제하지 않는다.
- 출력·Excel 패널: 필요한 CSV 기간·열·상세 수준을 줄이고 새로고침 부담을 확인한다.
- 운영 한도 상향은 성능·디스크 문제를 해결한 것으로 표시하지 않는다. 첫 버전의 경고·안내가 자동 DB 축소 기능을 뜻하지 않는다.
- 과거 이력·추정이 부족하면 권고의 불확실성도 표시하기.

80% 경고만으로 자동 삭제·자동 분할·원본 이동을 실행하지 않는다. 실제 공간 부족은 별도의 쓰기 차단 사유다.

화면 예시 — 아래는 실제 측정값이 아닌 설명용 수치다.

| 수익성 작업 공간 | 표시 예시 |
| --- | --- |
| 활성 DB 예산 사용 | DB 7.6 + WAL 0.5 = 8.1 / 10.0 GiB, **81% · 경고** |
| 디스크 가용 | 작업 경로 볼륨의 호출자 가용 23.4 GiB, 측정 시각·출처 표시 |
| 다음 월 반영 | 추가 피크 2.1 GiB 추정 · 표본 1회 · 신뢰도 낮음 |
| 추세 | 최근 월별 DB 증가와 적재·CSV 소요 시간, 비교 가능한 성공 이력만 |
| 대응 | DB 예산·보관 검토 / 이력 점유 검토 / Excel 출력 축소를 구분 |

80%는 정리 검토를 시작할 시점이다. 느려짐은 같은 규모의 적재·조회·CSV 생성 시간과 메모리/임시 공간으로 별도 판단한다.

## 6. 보관·분할 관리

첫 구현은 지표·경고와 대응 안내를 우선한다. 실제 보관·분할 도우미는 누적·검수·출력 흐름 안정화 후 구현한다.

- 과거 기간의 검증된 Parquet 보관본과 체크섬·모델/키/기간 메타데이터를 관리할 수 있게 한다.
- 보관과 DB 내 제거, 디스크 용량 회수는 서로 다른 작업이다. 기존 원본·DB·배포본을 임의 삭제하지 않는다.
- 연도별/업무별 분할을 검토하되 분석 범위·접근 빈도·실측을 근거로 선택한다. 자동 속도 향상을 약속하지 않는다.
- 후속으로 한 작업 공간을 여러 파일로 분할할 때 그 공간의 공통 키 등록부 권위를 유지하고, 기간→물리 저장 위치의 카탈로그와 전체 논리 조회를 보존한다. 서로 다른 작업 공간의 등록부를 통합한다는 뜻이 아니다.
- 여러 물리 DB 간 FK/원자성을 자동 보장한다고 가정하지 않는다. 지원 범위·검증·전환 방법을 분할 기능의 별도 설계/시험 대상으로 둔다.
- 과거 월 수정은 해당 보관/분할 위치로 정확히 반영해야 한다. 이전 보관본과 수정본이 둘 다 합산되지 않게 한다.
- 교차 연도 합계·대리키·행 수·기간 범위·대사 결과가 전후 동일한지 검증한 뒤 전환한다.
- 단순 행 삭제나 VACUUM이 파일을 반드시 줄인다고 안내하지 않는다. CHECKPOINT/재작성은 1.5.6 동작과 충분한 새 사본 공간을 확인한 관리 작업으로만 수행한다.
- 교체 전에 읽기/쓰기 연결을 정리하고 새 사본을 검증한다. 열린 사용자 DB나 WAL을 임의 복사·삭제하지 않는다.

## 7. 목적별 CSV와 승인

- 사용자는 이름·모델·기간·필터·분석 수준·표시 지표·집계 규칙을 정의한다. SQL 입력은 기본 요구가 아니다.
- 차원·팩트의 서로 다른 행 단위를 확인한 뒤 조인한다. 세로 손익 항목별로 수량이 반복 합산되지 않게 한다.
- 전체·변동·고정, 상세·소계의 중복 집계를 방지한다. 금액·재고·비율의 집계 특성을 유지한다.
- 결과 미리보기와 전체 검사 후 DB 리비전·모델·출력 정의에 결합된 승인 스냅샷을 만든다.
- 승인 이후 데이터/정의가 바뀌면 다시 검수한다. 실패 시 기존 공개 CSV를 보존한다.
- 첫 구현은 데이터셋별 완결된 단일 CSV와 고정 이름·열·형식 계약을 우선한다.
- 기본 형식은 UTF-8, 고정 헤더/열 순서·구분자·인용 규칙, 소수점 점·천단위 구분 없음이다. 코드와 월 수준 기간은 텍스트로 읽고 일 수준은 별도 형식을 선언한다. Excel 자동 형식 추정에 맡기지 않는다.
- 열 계약 변경은 출력 정의/계약 버전으로 관리하고 기존 연결을 조용히 깨뜨리지 않는다. 변경 출력과 템플릿을 검증한 뒤 전환하며 이전 공개 계약을 보존한다.
- 첫 기본 출력은 원본의 가로 지표를 유지한 단일 팩트의 평면 CSV다. 항목별 비용의 세로 출력에는 반복 수량을 넣지 않는다. 원본 자체의 반복값은 행 기준을 확인하기 전 임의 MAX/중복 제거로 보정하지 않는다.
- CSV/manifest 등 여러 원격 파일의 갱신을 하나의 트랜잭션으로 가정하지 않는다. 다중 파일이 반드시 함께 읽혀야 하는 출력은 버전 묶음·완료 선언·읽기 계약을 별도로 검증하기 전 공개하지 않는다.

### 7.1 Excel에서 지표 의미가 유지되는 조건

- CSV만으로 일반 피벗의 집계 방식을 강제할 수 없다. 가산 지표는 자유 집계용으로 제공하고 비율은 분자·분모에서 재계산한다. 비율 열의 단순 합계/평균을 정확한 분석으로 안내하지 않는다.
- 재고 잔액은 첫 기본 출력에서 단일 기준기간을 선택한다. 여러 기간의 비교·기말/평균·비율은 해당 측정값이 설정된 Excel 템플릿의 실제 동작을 검증한 경우에만 지원 완료로 표시한다.
- 다른 행 기준으로 출력할 때 반복 QTY가 합산되지 않게 한다. 같은 공간의 동반 팩트를 자동 생성하는 기능은 첫 최소 범위에 넣지 않는다.
- 템플릿은 실제 Excel에서 작성·검증한 기본 연결/데이터 모델 구조를 재사용하는 방안을 먼저 확인한다. 일반 XLSX 라이브러리만으로 Power Query·데이터 모델·측정값이 생성된다고 가정하지 않는다.
- 제작자 연결 정보를 매개변수로 관리하고 소비자는 본인 회사 계정으로 인증한다. 배포 템플릿에 제작자 인증정보를 넣지 않는다. 공개 저장소에는 회사 경로·자료를 포함한 실제 템플릿을 올리지 않는다.
- 앱의 정밀 대사와 Excel 표시/연산의 정밀도 한계를 구분한다. 템플릿의 피벗 결과도 원본/DB 통제값으로 검증한다.

## 8. SharePoint 사이트 주소와 Excel 연결

### 사용자 흐름

`사이트 주소 입력 → 회사 계정 로그인 → 배포 위치 확인·저장 → 데이터셋 게시 → 업로드/내용 확인 → Excel 연결`

- 사이트 주소가 기본 입력이다. 라이브러리/폴더의 후보를 탐색하고 저장된 프로필·명시적 기본 정책을 적용한다.
- 대상이 여럿이거나 기본값을 확정할 수 없으면 최초에 사용자가 표시 경로로 선택한다. 불투명한 내부 ID를 입력하게 하거나 임의 대상에 게시하지 않는다.
- 같은 배포 프로필을 여러 데이터셋에서 사용하며, 데이터셋마다 목적지·파일명을 관리할 수 있다.
- 인증·쓰기 권한·회사 앱 승인 조건은 초기에 실제 환경에서 검증한다. 사이트 주소 자체가 업로드 권한은 아니다.
- 회사 주소·기업 설정은 중앙 관리 지침을 따르며 인증 토큰·비밀을 공개 소스나 일반 설정 JSON에 저장하지 않는다.

### 구현·완료 기준

- 직접 업로드는 회사에서 승인한 Microsoft Graph/MSAL 경로를 검증한 뒤 구현한다. 필요하면 대용량 업로드 세션·재개·만료 처리를 사용한다.
- 원격 갱신 전 대상 ID·ETag·버전과 라이브러리 버전 관리 상태를 확인하고, 조건부 갱신으로 다른 게시자의 변경을 덮어쓰지 않게 한다. 임시 공개 파일+이름 변경을 원자적 교체로 안내하지 않는다.
- 충돌/412와 세션 중 변경은 대상 상태를 다시 조회해 표시한다. 자동 덮어쓰기 재시도나 무조건 이전 파일 재업로드를 하지 않는다. 업로드 시작 시의 조건 확인이 세션 전체 충돌 방지를 보장하는지는 현장에서 시험한다.
- 원격 파일의 크기·식별자·버전과 내용을 확인한다. 서버 해시가 있으면 같은 알고리즘으로 비교한다. SHA-256과 quickXorHash를 직접 비교하지 않는다.
- 같은 알고리즘을 사용할 수 없으면 읽기 재다운로드 비교 등 내용 검증 경로가 필요하다. 크기·ETag만 확인한 상태를 바이트 일치 검증 완료로 보고하지 않는다.
- 해시 검증 수준을 기록한다. quickXorHash 일치는 전송 오류 검사이며 암호학적 SHA-256 증명과 같지 않다. 재다운로드 검증은 추가 네트워크 비용을 표시한다.
- 상태를 `생성 → 승인 → 업로드 중 → 내용 검증 완료 / 업로드됐으나 미검증 / 실패`로 구분한다. 클라우드 완료 표시는 내용 검증이 끝난 경우에만 부여한다.
- 고정 CSV의 직접 교체는 원격 커밋 후 내용 검사에서 실패할 수 있다. 이때 이미 공개 파일이 바뀌었을 가능성을 숨기지 않는다. 이전 로컬 파일·원격 버전 정보를 보존하고, 후속 변경이 없을 때만 조건부 복구를 시도한다.
- '이전 원격본 보존: 확인됨/알 수 없음'을 별도 표시한다. 버전 관리 설정과 ID 기록만으로 실제 조회/복구 가능하다고 단정하지 않는다. 소비자 Excel의 새로고침 여부는 앱이 알 수 없으며 게시 완료와 구분한다.
- 검증 전 버전이 소비자에게 절대 노출되지 않아야 한다면, 불변 버전 파일+검증 완료 포인터와 이를 따르는 Excel 읽기 계약이 별도로 필요하다. 첫 고정 파일 방식이 이를 자동 보장한다고 설명하지 않는다.
- 회사 정책 때문에 API가 허용되지 않으면 직접 업로드 단계는 미완료로 표시한다. 동기화 폴더의 로컬 저장만으로 SharePoint 게시 완료라고 하지 않는다.
- 수동 업로드/동기화 폴더 내보내기는 명시적인 보조 경로다. 클라우드 반영을 확인하지 못하면 상태를 구분한다.
- 소비자 Excel은 SharePoint 사이트/폴더/파일을 회사 계정으로 읽는다. 제작자의 개인 동기화 경로를 연결에 넣지 않는다.
- 고정 구분자·문화권·날짜·코드 문자형·열 구조를 템플릿에서 명시한다. 큰 자료는 데이터 모델에 로드하고 메모리/새로고침 시간을 실측한다.
- 사이트 전체 파일 탐색과 원본 전체 다운로드를 최소화한다. 월별 파일 분할만으로 증분 새로고침을 보장하지 않는다.
- CSV에는 서버 쿼리 엔진이 없으므로 Excel의 필터를 DB로 보내 필요한 행만 조회하는 방식이 아니다. 분석용 CSV 자체를 사전 축소하고 파일 크기·행 수·전송량·새로고침 시간을 별도 관리한다.

SharePoint 인증·회사 승인 가능성은 0단계에서 먼저 확인한다. 실제 데이터 전송은 승인된 시험 자료로만 수행한다.
현재 첫 구현 범위는 0~5단계다. 6단계, 자유 드래그 모델 편집·SCD2·고급 값 매핑·거래 델타 갱신은 후속 확장으로 분리한다.
고정 GB 성능 약속이나 전체 구현 일정은 실측 없이 확정하지 않는다.

### 9.1 처음과 다음 달의 실제 사용자 동선

기존 DB 작업/배포 작업 공간 안에 단계를 배치한다. 기능마다 새 최상위 탭을 추가하지 않는다.

- 처음: 작업 이름 → 원본 선택 → 한 행의 의미·열 역할 → 차원/지표·기간/완성 규칙 → 전체 검사·공간 점검 → 첫 누적 → 대사/구조 확인 → 목적 CSV → 게시/Excel 연결.
- 다음 달: 작업 카드의 '새 자료 넣기' → 신규/수정/동일 자료와 구조 변화 확인 → 완성·공간 점검 → 실행·대사 → 영향받는 출력 재생성·검수·게시.
- 홈 카드: 어느 기간까지 확정됐는지, 새 자료, 데이터/출력/원격 게시의 최신 여부, 용량 상태와 다음 동작을 보여준다.
- 공통 상태: 준비됨 / 확인 필요 / 차단(해결 방법) / 실행 중 / 저장 확정 중 / 완료 / 실패 / 상태 확인 필요. 실패·중단 후에는 실제 리비전을 확인한 뒤 이전 자료 보존 여부를 안내한다.
- 표본 미리보기, DB 전체를 대상으로 한 조건 조회, 전체 대사를 구분한다. 큰 결과는 페이지로 읽고 UI 스레드에서 전체 테이블을 가져오지 않는다.
- 기존 BackgroundJobRunner와 Qt 어댑터를 재사용하되 작업의 DB 연결은 워커가 소유한다. DB 접근을 직렬화하고 쓰기 중에는 저장해 둔 표본만 보여준다. DB 조회/큰 대사는 대기시키고 결과의 리비전을 표시한다.
- 취소와 저장 확정 단계를 구분한다. interrupt·커밋 경계는 1.5.6에서 시험하며 취소 요청 자체를 롤백 완료로 보고하지 않는다.
- 첫 수직 시제품은 단일 팩트의 첫 적재→다음 월→과거 월 수정→대사→가산 CSV를 끝까지 연결한다. 이후 다른 구조/재고의 계약 검증과 시각적 검사·회사 배포를 확장한다.

## 10. 필수 검증 시나리오

- 월별 누적·수정: 1~4월 후 한 범위의 수정 2월만 반영, 나머지 기간·업무·분할의 키·합계 불변.
- 멱등성: 같은 파일/내용·같은 정의 재실행, 파일명만 변경, 정의 변경과 원본 변경의 구분.
- 입력 완성도: 한 월의 구성 파일 누락·추가·겹침, 실행 중 파일 변경, 명시적 취소/삭제 입력 구분.
- 모델: 수익성 외 일별 재고, 신규 거래선/제품 정상 등록과 기존 키 유지, 차원 정의 일치/충돌, 자연키 규칙 변경·재키잉 차단, 참조 불가/필수 키 누락 처리.
- 수치: USD/QTY 원본 대사, 소계·전체/변동/고정 중복 방지, 재고 잔액의 기간 합산 금지, 비율 재계산.
- 예산: 미설정·0/음수·단위 오류, 79.9%/80%/100% 경고, 75%에서는 유지·74.9%에서 해제, WAL 증가·측정 실패·오래된 값.
- 공간: DB/temp/output의 같은/다른 볼륨, 쿼터·가상 드라이브 미지원, 순차 대기열·다른 인스턴스 잠금, 추정 부족, 저용량 합성 볼륨의 적재·커밋·출력 실패 복구. 다중 작업 동시 예약은 후속 검증이다.
- 저장: 적재 중 중단·WAL 재시작·기존 성공본 보존, 보관본 훼손과 부족한 재작성 공간.
- 게시: 로그인 실패·권한 없음·여러 대상·세션 만료·중단·내용 불일치·DB 리비전 변경·클라우드 미확인 상태.
- Excel: 다른 사용자가 템플릿을 로컬 저장한 뒤 본인 계정으로 새로고침, 선행 0·USD·QTY·기간 유지.
- 원자성·복구: 데이터/키/범위 상태/성공 이력의 커밋 일치, 이전 행·속성 감사 사본 검증, 비대상 범위 불변, 앱 재시작 후 중단 상태 조정. 행 수 항등식만으로 값의 대사를 대체하지 않는다.
- 관측: WAL 없음과 접근 실패 구분, 부분 합계·오래된 값·한도 미설정 표시, 분할 후 합산 경고 유지, %의 바이트 단위/경계값 일치.
- 원격 충돌: 다른 게시자의 변경·조건부 갱신 실패, 업로드 후 검증 실패·복구 불가 상태, 버전/해시 알고리즘과 Excel 실제 읽기 결과 구분.
- 의미·변경: 과거 월 수정 후 최신 속성 불변, 같은 기준시점 상충, 새 비용 열 누락 방지, NULL과 0 구분, 다른 작업 공간의 동일 SK 조인 차단.
- Excel 집계: 가산 합계, 분자/분모 비율, 재고 단일기간/검증된 다기간 템플릿, 항목 전개 후 수량 중복 방지, 실제 연결 템플릿의 로컬 저장·재인증.
- 복구·비용: 범위 사본과 전체 손상 복구 구분, 오래된 외부 복구 목록 탐지, 일관 백업의 복원 리비전, 작업마다 불필요한 전체 DB 재스캔을 하지 않는지 확인.

자동 검사는 합성·격리 자료로 수행하고, 기존 `scripts/check.ps1` 및 Windows 설치 검증을 유지한다.
실제 회사 SharePoint/Excel·Application Control·큰 원본 성능은 별도 현장 게이트다.

### 10.1 4차 논의의 반례와 기대 동작

아래 수치는 설명/시험 설계용이며 실행 결과가 아니다.

| 사례 | 기대 동작 |
| --- | --- |
| A. DB 7.6 + WAL 0.5 / 예산 10 GiB | 81% 권고 경고. 실제 쓰기 허용은 디스크/피크 점검으로 따로 판단. CSV 축소로 이 비율은 줄지 않음 |
| B. 사용률 40%, 가용 0.7, 추가 피크 3, 잔여 여유 2 GiB | 공간 부족으로 쓰기 차단. 예산 상향으로 해제할 수 없음. 잔여 2 GiB는 시험용 제안값 |
| C. WAL 없음/접근 실패, 예산 미설정 | 실제 없음은 0. 실패는 부분 합계와 알 수 없음. 예산 없으면 % 없음. 필수 상태 확인 불가 시 쓰기 보류 |
| D. 후속 분할 파일은 각각 80% 미만이나 합계 초과 | 같은 작업 공간의 활성 DB+WAL 총합으로 경고. 보관본·디스크 여유는 따로 표시 |
| E. 수정 2월 일부 누락·실행 중 변경·새 비용 열 | 불완전/불일치 입력은 확정 전 차단. 다른 월 보존. 새 열을 분류하기 전 무시하지 않으며 과거 미보고는 NULL |
| F. 4월 최신 속성 뒤 2월 정정, DB 손상 | 2월 팩트만 검수 후 교체, 최신 속성 자동 회귀 금지. 확정 후 undo 없음. 손상은 검증된 복원 지점과 확인 가능한 이후 자료로 별도 처리 |
| G. 비용 전개 QTY·다기간 재고·이익률 피벗 | 기본 가산 CSV, 비용 세로형은 QTY 제외. 재고 단일 기준기간. 비율/다기간 측정값은 실제 템플릿 검증까지 완료로 표시하지 않음 |
| H. 업로드 후 내용 실패·ETag 충돌 | 원격 최신 상태를 확인하고 실패/미검증 표시. 이전 원격본 보존·조건부 복구 가능성·소비자 새로고침을 각각 구분 |

## 12. 구현 전에 정할 운영값

계획에는 선택 지점을 남기고 임의의 회사 환경·데이터 크기를 기본값으로 확정하지 않는다.

- 작업 공간별 운영 예산 B: 대표 자료의 증가량·처리시간·디스크 쿼터를 보고 설정. 연간/3개년 기간은 실측 후 결정.
- 최소 잔여 공간: 2 GiB는 검증 전 제안이며 작업 피크와 별도다. 성능 목표·최대 작업 범위·추정 부족 시 처리 정책을 함께 확정.
- 입력 완성 선언과 통제합계의 책임자, 수정 범위와 의도적인 0건 처리 방식.
- 이전 행/차원 변경 이력의 저장 위치·보존 개수/기간과 복구 절차. 사용자 자료 자동 삭제는 기본값으로 넣지 않음.
- 차원 최신 속성 덮어쓰기의 과거 분석 영향 허용 여부, 누락 키 예외 정책.
- SharePoint 앱 승인/인증 담당, 대상 라이브러리·버전 관리·배포 프로필 책임자, 해시 검증/재다운로드 비용과 검증 전 노출 허용 수준.
- Excel 시트/데이터 모델 적재 대상·실측 가능한 새로고침 목표. 연결된 범위를 벗어난 분석은 출력 정의를 추가하거나 수정.
