# 디렉터리·빌드 파이프라인 정상화 검수 — 2026-10-07

대상은 Data Refinery 2.0.1의 저장소 구조와 Windows 배포 절차입니다. 화면 기능이나
사용자의 업무 데이터는 변경하지 않았습니다. 기존 게시 버전은 보존하고, 다음 버전부터
일원화된 빌드·서명 절차를 사용합니다.

## 판정

구조 정상화와 로컬 배포 검증을 완료했습니다. 실제 Claude CLI의
`claude-opus-5-5`로 1차 검수와 두 차례 후속 검수를 받았습니다. 최종 응답의
`modelUsage`에는 canonical model `claude-opus-5-5`, provider `firstParty`,
`is_error=false`가 기록되어 있습니다. 최종 읽기 전용 검수는 남은 P0/P1/P2가 없다고
판정했습니다. 이 모델의 소스 검수와 아래에서 직접 실행한 검증을 구분합니다.

새로운 개인 키 서명이나 기존 v2.0.1 재게시를 수행한 결과는 아닙니다.

## 구조와 용량

| 항목 | 이전 | 현재 |
| --- | --- | --- |
| 설치 설계도 | `release/installer/DataRefinery.iss` | `installer/setup.iss` |
| PyInstaller spec | `release/packaging/` | `installer/` |
| 공식 빌드·서명 진입점 | 개별 빌드/서명/후처리 스크립트 | `scripts/build.ps1`, `scripts/sign.ps1` |
| 빌드 임시 공간 | `release/build`, `release/dist` | 루트 `build`, `dist` (Git 제외) |
| 릴리즈 노트 원본 | `release/`의 여러 버전 | `docs/release-notes/` |
| 최신 공식 배포 폴더 | 임시 파일과 배포물 혼재, 약 2.42 GiB | `release/`에 최신 파일 9개, 하위 폴더 없음 |

기존 임시 디렉터리는 합계 약 2,475.09 MiB였습니다. 정리 전 서명 배포물·서명 기록·
인증서·작업 자료 등 보호 대상 55개를 해시 검증하고 Git에서 제외된
`tools/release-history/`에 중복을 제거한 보관본과 이관 목록을 남겼습니다.
그 보관본은 약 519.65 MiB이며 이번 정리에서 삭제하지 않았습니다.

현재 `release/`의 파일 목록 합계는 약 139.04 MiB입니다. 두 설치 이름은 NTFS 하드
링크로 같은 파일 내용을 공유하므로 중복을 제외한 내용 용량은 약 75.23 MiB입니다.
다른 파일시스템에 복사하거나 GitHub에 두 이름으로 업로드하면 각각의 전체 파일이
필요할 수 있습니다. 파일 목록 합계와 중복을 제외한 내용 용량을 혼동하지 않습니다.

최신 파일은 두 설치 명칭, 런처, 바이너리별 `.sha256` 3개, `SHA256SUMS.txt`,
`build-manifest.json`, 최신 릴리즈 노트입니다. 기존 설치 파일과 런처의 서명된 바이트는
유지했습니다. 배포 폴더를 재생성해도 공식 버전의 원래 소스 커밋을 매니페스트에 유지합니다.

## 지적 사항과 수정

| 우선순위 | 확인한 문제 | 수정과 검증 |
| --- | --- | --- |
| P1 | PowerShell 5.1에서 없는 태그의 stderr가 서명 진입을 중단 | 조용한 태그 조회와 명시적 종료 코드 처리; 실제 가짜 native 명령의 stderr 회귀 검사 |
| P1 | 릴리즈 조회 실패 및 빈 JSON 배열의 처리 오류 | 조회 실패를 부재로 간주하지 않음; 빈 배열을 0개로 처리하고 CI 검색 재시도 |
| P1 | 비공개 초안을 게시된 릴리즈 전용 tag API로 조회 | 인증된 `gh release view`로 ID를 찾고 정확한 저장소의 숫자 ID만 조회; 신규 초안과 업로드 재개 검사 |
| P2 | 태그가 있는 버전 재서명 및 업로드 중단 후 복구 곤란 | 재서명 거부; `-PublishOnly`로 동일 커밋·검증 파일만 누락분 업로드; 변경된 원격 파일과 `--clobber` 거부 |
| P2 | 테스트 생략 또는 오래된 빌드 기록으로 서명 가능 | 빌드 시작 시 기존 기록 무효화; `testsPassed`와 깨끗한 정확한 소스 커밋 확인 |
| P2 | 사용자 선택 설치 위치와 고정 UserSetting 위치가 불일치 | 기본 설치 경로를 고정하고 경로 선택 화면 제거; CI의 명시적 `/DIR`만 격리 설치 검사에 사용 |
| 후속 확인 | Inno 6.7.3의 ISCC 파일 속성이 버전 0.0.0.0 | 설치 설계도의 `VER`로 실제 컴파일러 최소 버전을 검사; 실제 컴파일 통과 |

평면 배포 폴더·숨김 항목·연결 경로, 매니페스트의 바이너리 누락, 체크섬 전체 범위,
사이드카 바이트 형식/BOM, 노트 원본 일치, 작업 사본 해시, 타임스탬프와 게시자를
검증합니다. 서명 도구의 Microsoft 서명도 확인합니다. Inno가 삭제할 임시 서명 제거
프로그램은 콜백에서 미리 보관하고 검증합니다. 기존 공식 폴더는 모든 검사 후 교체하며,
교체 실패는 이전 폴더로 되돌립니다.

## 직접 실행한 검증

| 검증 | 결과 | 범위 |
| --- | --- | --- |
| 전체 Python 테스트 | 528개 실행, 527개 통과, 선택 Excel COM 1개 건너뜀 | 격리 AppData를 사용하는 기본 빌드 절차 |
| PowerShell 5.1 실패 주입 검사 | 35개 통과 | 서명/해시/별칭/매니페스트/초안 생성·재개, 개인 키·네트워크 미사용 |
| PyInstaller·Inno 빌드 | 앱 onedir, 런처, 두 명칭 설치 검증본 생성 성공 | 고정 의존성 환경, Inno 6.7.3; 미서명 검증본은 `dist/staging` |
| 기존 공식 v2.0.1 검사 | 두 설치 이름과 런처 모두 통과 | 실제 Authenticode `Valid`, RFC3161, `signtool verify /pa /all`, 게시자, 해시·매니페스트·노트 |
| 기존 GitHub v2.0.1 조회 | 기존 태그 커밋과 배포 바이너리 digest 유지, 공개 자산 6개 | 읽기 전용 API 확인; 이번 로컬 별칭·매니페스트를 기존 릴리즈에 덮어쓰지 않음 |

CI는 `windows-release-check.yml`에서 Python·배포 실패 검사, 통일된 빌드, 격리된
Windows 설치·재설치·제거 검사를 수행합니다. 설정 내용 해시와 로그·데이터셋 표식이
재설치와 제거 후에도 유지되는지 확인합니다. CI의 설치 검증본은 미서명이며 테스트
생략 빌드 기록은 실제 서명 입력으로 사용할 수 없습니다.

검증 로그·모델 응답·보관 목록은 Git에서 제외된 로컬 `tools/`에 남깁니다.

## 유지하는 규칙과 경계

- 설치는 `%LOCALAPPDATA%\Programs\Data Refinery`, 관리 자료는 그 안의 `UserSetting`,
  작업 DB는 `UserSetting\datasets`입니다. `src/app_paths.py`와 설치 설계도가 일치합니다.
  원본을 보존하는 기존 이관 정책은 유지합니다.
- 기존 서명 배포본·사용자 자료·공유 분석 데이터·레거시 Tkinter 기능을 보존합니다.
  보호 보관본은 일반 캐시 삭제 대상으로 포함하지 않습니다.
- 새 SimplySign/KSP 개인 키 호출은 사용자가 로그인한 대화형 관리자 PowerShell에서
  실제 새 버전 서명 시 확인해야 합니다. 모의 검사와 기존 서명 검증은 새 서명 성공을
  증명하지 않습니다. 새 GitHub 초안 업로드는 모의 검사로 확인했고 실게시를 하지 않았습니다.
- 실제 Excel 연결과 수동 GUI 사용은 이번 구조 변경 검증 범위에 없습니다.
- 서명 실패 중간 파일은 보존합니다. GitHub 업로드 실패의 `starter` 잔여 자산은 확인 후
  수동 삭제해야 재개됩니다. 설치된 과거 버전 실행 파일·라이브러리 정리는 별도 검토 대상입니다.
- PATH가 오래된 ISCC를 먼저 가리키면 안전하게 실패합니다. 사용 도구를 PATH에서 정리해야 합니다.

공식 운영 절차는 [releasing.md](releasing.md), 구조 규칙은
[project-structure.md](project-structure.md)를 따릅니다.
